# GitLab CI/CD - Comprehensive `.gitlab-ci.yml` Guide

## 1. What is `.gitlab-ci.yml`?
A YAML file that defines your CI/CD pipeline:
- Stages (order of execution) or (structure of pipeline)
- Jobs (tasks)
- Rules (when to run)

---

## 2. Core Structure

```yaml
# ==============================
# GLOBAL CONFIGURATION
# ==============================

image: <docker_image>              # e.g., python:3.12 / node:18 / ubuntu:22.04

services:
  - <service_name>                # e.g., postgres:15, redis:latest

stages:
  - <stage_1>                     # e.g., build
  - <stage_2>                     # e.g., test
  - <stage_3>                     # e.g., deploy

variables:
  <VARIABLE_NAME>: "<value>"      # e.g., DEBUG: "false"
  <ANOTHER_VARIABLE>: "<value>"

cache:
  key: <cache_key>                # optional
  paths:
    - <cache_path_1>              # e.g., .venv/
    - <cache_path_2>

before_script:
  - <setup_command_1>             # e.g., pip install -r requirements.txt
  - <setup_command_2>

after_script:
  - <cleanup_command>             # optional

# ==============================
# JOB 1
# ==============================

<job_name_1>:
  stage: <stage_1>                # must match stages
  script:
    - <command_1>
    - <command_2>

  rules:
    - if: '$CI_COMMIT_BRANCH == "<branch_name>"'
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

  only:
    - <branch_name>               # e.g., main

  except:
    - <excluded_branch>

  needs:                          # This job depends on the completion of the specified job(s) and can start immediately after they finish (enables parallel execution)
    - <job_name_dependency>

  artifacts:
    name: "<artifact_name>"       # optional (default: auto-generated)
    paths:                        # Required
      - <file_path_1>             # e.g., build/
      - <file_path_2>
    expire_in: <time>             # optional (default: never expires immediately) e.g., 1 week
    when: <on_success | on_failure | always>   # optional (default: on_success)


  cache:
    paths:
      - <cache_path>

  tags:
    - <runner_tag>                # e.g., docker, linux

  environment:
    name: <environment_name>      # e.g., production, staging
    url: <environment_url>        # optional

  when: <on_success | manual | always | delayed>
  allow_failure: <true | false>

  retry:
    max: <number>                 # e.g., 2
    when:
      - runner_system_failure

  timeout: <time>                 # e.g., 10m

# ==============================
# JOB 2
# ==============================

<job_name_2>:
  stage: <stage_2>
  script:
    - <command>

# ==============================
# JOB 3
# ==============================

<job_name_3>:
  stage: <stage_3>
  script:
    - <command>
```

---

**Best practice to use `needs`:** 
```yml
stages:
  - build
  - test
  - deploy

job_a:
  stage: build
  script: echo "build"

job_b:
  stage: test
  needs:
    - job: job_a
```
This pipeline builds in job_a, then job_b starts testing immediately after job_a finishes using needs, instead of waiting for the full build stage to complete.

## Full Production Template

```yaml
image: python:3.12

stages:
  - build
  - test
  - deploy

variables:
  PYTHONUNBUFFERED: "1"

cache:
  paths:
    - .cache/pip

before_script:
  - pip install -r requirements.txt

build:
  stage: build
  script:
    - echo "Build step"

test:
  stage: test
  script:
    - python manage.py test

deploy:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

## Explanations: 

This pipeline:

1. Uses Python Docker image
2. Installs dependencies
3. Runs build → test → deploy
4. Deploys only on main branch

---

## i. Docker image

```yaml
image: python:3.12
```

Meaning:

- Every job runs inside a Python 3.12 container
- You don’t need to install Python manually

---

## ii. Stages (pipeline structure)

```yaml
stages:
  - build
  - test
  - deploy
```

Meaning:

build → test → deploy

This defines the pipeline execution flow.

---

## iii. Global variables

```yaml
variables:
  PYTHONUNBUFFERED: "1"
```

Meaning:

- Forces Python to print logs immediately
- No buffering (useful for CI logs)

---

## iv. Cache

```yaml
cache:
  paths:
    - .cache/pip
```

Meaning:

- Saves downloaded pip packages
- Reuses them in future pipeline runs
- Speeds up installation

---

## v. before_script (runs before every job)

```yaml
before_script:
  - pip install -r requirements.txt
```

Meaning:

This runs automatically before:

- build
- test
- deploy

So each job starts with dependencies installed.

---

## vi. Build job

```yaml
build:
  stage: build
  script:
    - echo "Build step"
```

Meaning:

- Runs in build stage
- Currently just prints a message
- In real projects: compile, collect static files, build artifacts

---

## vii. Test job

```yaml
test:
  stage: test
  script:
    - python manage.py test
```

Meaning:

- Runs Django tests
- Checks if code is working correctly

---

## viii. Deploy job

```yaml
deploy:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

Meaning:

- Runs only when branch is main
- Prevents accidental deployments from other branches

## Variables
GitLab CI/CD uses various types of variables to make pipelines dynamic, adaptable and secure. Variables can store values such as paths, URLs or secret credentials. 
```yml
image: python:3.11

# Global variable
variables:
  GLOBAL_VAR: "I am global"

stages:
  - test

test_job:
  stage: test

  # Job-level variable
  variables:
    JOB_VAR: "I am job-specific"

  script:
    - echo "Global: $GLOBAL_VAR"
    - echo "Job: $JOB_VAR"
    - echo "Secret: $SECRET_VAR"
```
- GitLab UI Variable (we must add manually)
Go to:
```
Settings -> CI/CD -> Variables
```

Add:
```
KEY: SECRET_VAR
VALUE: mysecret123
```
(Enable ✅ Masked)

**Expected Output in Pipeline Logs**
```
Global: I am global
Job: I am job-specific
Secret: ****
```
```
What’s happening here
GLOBAL_VAR -> available everywhere
JOB_VAR -> only inside test_job
SECRET_VAR -> comes from GitLab UI (secure)
```

# GitLab CI/CD Predefined Variables (Must-Know)

## 1. Branch / Tag / Commit

-   CI_COMMIT_BRANCH → Branch name
-   CI_COMMIT_TAG → Tag name
-   CI_COMMIT_MESSAGE → Commit message
-   CI_COMMIT_SHA → Full commit hash
-   CI_COMMIT_SHORT_SHA → Short hash

## 2. Pipeline Info

-   CI_PIPELINE_ID → Unique pipeline ID
-   CI_PIPELINE_IID → Project-level pipeline ID
-   CI_PIPELINE_SOURCE → Trigger source (push, merge_request_event,
    schedule, web)

## 3. Project Info

-   CI_PROJECT_NAME → Project name
-   CI_PROJECT_PATH → group/project
-   CI_PROJECT_DIR → Working directory

## 4. User Info

-   GITLAB_USER_NAME → Triggered by user
-   GITLAB_USER_EMAIL → User email

## 5. Runner Info

-   CI_RUNNER_ID → Runner ID
-   CI_RUNNER_DESCRIPTION → Runner name

## 6. Environment Variables

-   CI_ENVIRONMENT_NAME → Environment name (dev/staging/prod)
-   CI_ENVIRONMENT_URL → Environment URL

## 7. Merge Request Variables

-   CI_MERGE_REQUEST_ID → MR ID
-   CI_MERGE_REQUEST_SOURCE_BRANCH_NAME → Source branch
-   CI_MERGE_REQUEST_TARGET_BRANCH_NAME → Target branch

## 8. Job Info

-   CI_JOB_ID → Job ID
-   CI_JOB_NAME → Job name
-   CI_JOB_STAGE → Stage name

## Common Use Cases

### Deploy only on main

``` yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "main"'
```

### Detect tag deployment

``` yaml
rules:
  - if: '$CI_COMMIT_TAG'
```

### Skip deploy using commit message

``` yaml
rules:
  - if: '$CI_COMMIT_MESSAGE =~ /skip deploy/i'
    when: never
```

### Detect merge request pipeline

``` yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

## Key Tips

-   Variables are automatically provided by GitLab
-   They are case-sensitive
-   Some variables may be empty depending on pipeline type
```
script:
  - echo $CI_COMMIT_BRANCH        # Current branch name
  - echo $CI_COMMIT_MESSAGE       # Tag name (if pipeline from tag)
  - echo $CI_COMMIT_SHA           # Full commit hash
  - CI_COMMIT_SHORT_SHA           # Short hash
  - echo $CI_PIPELINE_ID          # Commit message
  - echo $CI_PROJECT_NAME         # Unique pipeline ID
  - echo $CI_PROJECT_NAME         # Project name
```

## Example of CI/CD pipeline (Follow best practices)
```yml
image: python:3.12

stages:
  - setup
  - lint
  - test
  - build
  - deploy

variables:
  PYTHONUNBUFFERED: "1"
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
  DJANGO_SETTINGS_MODULE: "config.settings"
  VENV_DIR: "$CI_PROJECT_DIR/.venv"

cache:
  key:
    files:
      - requirements.txt
  paths:
    - .cache/pip

# --------------------
# SETUP (INSTALL ONCE)
# --------------------
setup:
  stage: setup
  script:
    - python -m venv $VENV_DIR
    - source $VENV_DIR/bin/activate
    - pip install --upgrade pip
    - pip install -r requirements.txt
  artifacts:
    paths:
      - .venv/
    expire_in: 1 hour

# --------------------
# LINT
# --------------------
lint:
  stage: lint
  dependencies:
    - setup
  script:
    - source $VENV_DIR/bin/activate
    - pip install flake8
    - flake8 .
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" || $CI_COMMIT_BRANCH'

# --------------------
# TEST
# --------------------
test:
  stage: test
  dependencies:
    - setup
  script:
    - source $VENV_DIR/bin/activate
    - python manage.py migrate
    - python manage.py test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" || $CI_COMMIT_BRANCH'

# --------------------
# BUILD
# --------------------
build:
  stage: build
  dependencies:
    - setup
  script:
    - source $VENV_DIR/bin/activate
    - python manage.py collectstatic --noinput
  artifacts:
    paths:
      - staticfiles/
    expire_in: 1 day
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

# --------------------
# DEPLOY
# --------------------
deploy_production:
  stage: deploy
  script:
    - echo "Deploying Django app..."
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```
