# GitLab CI/CD - Comprehensive `.gitlab-ci.yml` Guide

## 1. What is `.gitlab-ci.yml`?
A YAML file that defines your CI/CD pipeline:
- Stages (order of execution) or (structure of pipeline)
- Jobs (tasks)
- Rules (when to run)

---

## 2. Core Structure

```yaml
# ==============================
# GLOBAL CONFIGURATION
# ==============================

image: <docker_image>              # e.g., python:3.12 / node:18 / ubuntu:22.04

services:
  - <service_name>                # e.g., postgres:15, redis:latest

stages:
  - <stage_1>                     # e.g., build
  - <stage_2>                     # e.g., test
  - <stage_3>                     # e.g., deploy

variables:
  <VARIABLE_NAME>: "<value>"      # e.g., DEBUG: "false"
  <ANOTHER_VARIABLE>: "<value>"

cache:
  key: <cache_key>                # optional
  paths:
    - <cache_path_1>              # e.g., .venv/
    - <cache_path_2>

before_script:
  - <setup_command_1>             # e.g., pip install -r requirements.txt
  - <setup_command_2>

after_script:
  - <cleanup_command>             # optional

# ==============================
# JOB 1
# ==============================

<job_name_1>:
  stage: <stage_1>                # must match stages
  script:
    - <command_1>
    - <command_2>

  rules:
    - if: '$CI_COMMIT_BRANCH == "<branch_name>"'
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

  only:
    - <branch_name>               # e.g., main

  except:
    - <excluded_branch>

  needs:                          # This job depends on the completion of the specified job(s) and can start immediately after they finish (enables parallel execution)
    - <job_name_dependency>

  artifacts:
    name: "<artifact_name>"       # optional (default: auto-generated)
    paths:                        # Required
      - <file_path_1>             # e.g., build/
      - <file_path_2>
    expire_in: <time>             # optional (default: never expires immediately) e.g., 1 week
    when: <on_success | on_failure | always>   # optional (default: on_success)


  cache:
    paths:
      - <cache_path>

  tags:
    - <runner_tag>                # e.g., docker, linux

  environment:
    name: <environment_name>      # e.g., production, staging
    url: <environment_url>        # optional

  when: <on_success | manual | always | delayed>
  allow_failure: <true | false>

  retry:
    max: <number>                 # e.g., 2
    when:
      - runner_system_failure

  timeout: <time>                 # e.g., 10m

# ==============================
# JOB 2
# ==============================

<job_name_2>:
  stage: <stage_2>
  script:
    - <command>

# ==============================
# JOB 3
# ==============================

<job_name_3>:
  stage: <stage_3>
  script:
    - <command>
```

---

**Best practice to use `needs`:** 
```yml
stages:
  - build
  - test
  - deploy

job_a:
  stage: build
  script: echo "build"

job_b:
  stage: test
  needs:
    - job: job_a
```
This pipeline builds in job_a, then job_b starts testing immediately after job_a finishes using needs, instead of waiting for the full build stage to complete.

## Full Production Template

```yaml
image: python:3.12

stages:
  - build
  - test
  - deploy

variables:
  PYTHONUNBUFFERED: "1"

cache:
  paths:
    - .cache/pip

before_script:
  - pip install -r requirements.txt

build:
  stage: build
  script:
    - echo "Build step"

test:
  stage: test
  script:
    - python manage.py test

deploy:
  stage: deploy
  script:
    - echo "Deploying..."
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

## Explanations: 

This pipeline:

1. Uses Python Docker image
2. Installs dependencies
3. Runs build → test → deploy
4. Deploys only on main branch

```yaml

  - build
```

Meaning:

build → test → deploy

This defines the pipeline execution flow.

## iii. Global variables

```yaml

```

Meaning:

## iv. Cache

```yaml

  paths:
    - .cache/pip
```

Meaning:

- Saves downloaded pip packages
- Reuses them in future pipeline runs
- Speeds up installation

## v. before_script (runs before every job)

Meaning:

This runs automatically before:

## Variables
GitLab CI/CD uses various types of variables to make pipelines dynamic, adaptable and secure. Variables can store values such as paths, URLs or secret credentials. 
```yml
image: python:3.11

# Global variable
variables:
  GLOBAL_VAR: "I am global"

stages:
  - test

test_job:
  stage: test

  # Job-level variable
  variables:
    JOB_VAR: "I am job-specific"

  script:
    - echo "Global: $GLOBAL_VAR"
    - echo "Job: $JOB_VAR"
    - echo "Secret: $SECRET_VAR"
```
- GitLab UI Variable (we must add manually)
Go to:
```
Settings -> CI/CD -> Variables
```

Add:
```
KEY: SECRET_VAR
VALUE: mysecret123
```
(Enable ✅ Masked)

**Expected Output in Pipeline Logs**
```
Global: I am global
Job: I am job-specific
Secret: ****
```
```
What’s happening here
GLOBAL_VAR -> available everywhere
JOB_VAR -> only inside test_job
SECRET_VAR -> comes from GitLab UI (secure)
```

# GitLab CI/CD Predefined Variables (Must-Know)

## 1. Branch / Tag / Commit

-   CI_COMMIT_BRANCH → Branch name
-   CI_COMMIT_TAG → Tag name
-   CI_COMMIT_MESSAGE → Commit message
-   CI_COMMIT_SHA → Full commit hash
-   CI_COMMIT_SHORT_SHA → Short hash

## 2. Pipeline Info

-   CI_PIPELINE_ID → Unique pipeline ID
-   CI_PIPELINE_IID → Project-level pipeline ID
-   CI_PIPELINE_SOURCE → Trigger source (push, merge_request_event,
    schedule, web)

## 3. Project Info

-   CI_PROJECT_NAME → Project name
-   CI_PROJECT_PATH → group/project
-   CI_PROJECT_DIR → Working directory

## 4. User Info

-   GITLAB_USER_NAME → Triggered by user
-   GITLAB_USER_EMAIL → User email

## 5. Runner Info

-   CI_RUNNER_ID → Runner ID
-   CI_RUNNER_DESCRIPTION → Runner name

## 6. Environment Variables

-   CI_ENVIRONMENT_NAME → Environment name (dev/staging/prod)
-   CI_ENVIRONMENT_URL → Environment URL

## 7. Merge Request Variables

-   CI_MERGE_REQUEST_ID → MR ID
-   CI_MERGE_REQUEST_SOURCE_BRANCH_NAME → Source branch
-   CI_MERGE_REQUEST_TARGET_BRANCH_NAME → Target branch

## 8. Job Info

-   CI_JOB_ID → Job ID
-   CI_JOB_NAME → Job name
-   CI_JOB_STAGE → Stage name

## Common Use Cases

### Deploy only on main

``` yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "main"'
```

### Detect tag deployment

``` yaml
rules:
  - if: '$CI_COMMIT_TAG'
```

### Skip deploy using commit message

``` yaml
rules:
  - if: '$CI_COMMIT_MESSAGE =~ /skip deploy/i'
    when: never
```

### Detect merge request pipeline

``` yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

-   Some variables may be empty depending on pipeline type

```
  - echo $CI_PIPELINE_ID          # Commit message
  - echo $CI_PROJECT_NAME         # Unique pipeline ID
  - echo $CI_PROJECT_NAME         # Project name
```

## Example of CI/CD pipeline (Follow best practices)
```yml
image: python:3.12

stages:
  - setup
  - lint
  - test
  - build
  - deploy

variables:
  PYTHONUNBUFFERED: "1"
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"
  DJANGO_SETTINGS_MODULE: "config.settings"
  VENV_DIR: "$CI_PROJECT_DIR/.venv"

cache:
  key:
    files:
      - requirements.txt
  paths:
    - .cache/pip

# --------------------
# SETUP (INSTALL ONCE)
# --------------------
setup:
  stage: setup
  script:
    - python -m venv $VENV_DIR
    - source $VENV_DIR/bin/activate
    - pip install --upgrade pip
    - pip install -r requirements.txt
  artifacts:
    paths:
      - .venv/
    expire_in: 1 hour

# --------------------
# LINT
# --------------------
lint:
  stage: lint
  needs:
    - setup
  script:
    - source $VENV_DIR/bin/activate
    - pip install flake8
    - flake8 .
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" || $CI_COMMIT_BRANCH'

# --------------------
# TEST
# --------------------
test:
  stage: test
  needs:
    - setup
  script:
    - source $VENV_DIR/bin/activate
    - python manage.py migrate
    - python manage.py test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" || $CI_COMMIT_BRANCH'

# --------------------
# BUILD
# --------------------
build:
  stage: build
  needs:
    - setup
  script:
    - source $VENV_DIR/bin/activate
    - python manage.py collectstatic --noinput
  artifacts:
    paths:
      - staticfiles/
    expire_in: 1 day
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

# --------------------
# DEPLOY
# --------------------
deploy_production:
  stage: deploy
  script:
    - echo "Deploying Django app..."
  environment:
    name: production
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```

```yml
# ════════════════════════════════════════════════════════════
# WHAT IS THIS FILE?
# GitLab reads this file automatically when you push code.
# It defines your pipeline - a series of automated steps
# that install, check, test, build and deploy your app.
# ════════════════════════════════════════════════════════════


# ── STAGES ──────────────────────────────────────────────────
# Think of stages as phases in an assembly line.
# They always run LEFT TO RIGHT in this order.
# If a stage fails, the next stage does NOT run (unless told otherwise).
stages:
  - install   # Phase 1: download libraries our app needs
  - lint      # Phase 2: check code style/mistakes
  - test      # Phase 3: run automated tests
  - build     # Phase 4: package the app for delivery
  - deploy    # Phase 5: ship it!


# ── VARIABLES ───────────────────────────────────────────────
# Variables are reusable values, like constants in code.
# $CI_PROJECT_DIR is a built-in GitLab variable = your repo folder path.
# We tell pip (Python package manager) to store downloads here
# so we can reuse them later without re-downloading.
variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.pip-cache"


# ── CACHE ───────────────────────────────────────────────────
# Cache saves folders between pipeline runs.
# Without cache: every pipeline downloads all packages from scratch (slow).
# With cache:    second run reuses what was already downloaded (fast).
# .pip-cache/ = downloaded package files
# venv/        = the installed Python virtual environment
cache:
  paths:
    - .pip-cache/
    - venv/


# ════════════════════════════════════════════════════════════
# STAGE 1: INSTALL
# Download and install all Python libraries listed in requirements.txt
# ════════════════════════════════════════════════════════════
install-deps:
  stage: install

  # "image" = which Docker container to run this job inside.
  # python:3.11-alpine is a tiny Linux container with Python 3.11 pre-installed.
  # Every job gets a fresh container - nothing carries over automatically.
  image: python:3.11-alpine

  script:
    # Create a virtual environment (isolated folder of Python packages).
    # This prevents package conflicts between projects.
    - python -m venv venv

    # Activate the virtual environment.
    # After this, "pip" and "python" commands use the venv versions.
    - source venv/bin/activate

    # Install everything listed in requirements.txt (pytest, pytest-cov etc.)
    - pip install -r requirements.txt

  # ARTIFACTS = files to save and pass to the next stage.
  # Since each job runs in a fresh container, files are lost when a job ends.
  # Artifacts solve this - GitLab uploads them and makes them available
  # to all later jobs in the pipeline.
  artifacts:
    paths:
      - venv/         # Save the whole virtual environment folder
    expire_in: 1 hour # Auto-delete after 1 hour (we only need it for this pipeline)


# ════════════════════════════════════════════════════════════
# STAGE 2: LINT
# Lint = automatically check code for obvious errors and bad style.
# Example: unused imports, undefined variables, syntax mistakes.
# ════════════════════════════════════════════════════════════
lint-code:
  stage: lint
  image: python:3.11-alpine

  # allow_failure: true means:
  # "If this job fails, show a warning but keep the pipeline running."
  # Perfect for lint - we want to SEE the warnings but not block deployment.
  # Try changing this to false and introducing a typo in app.py!
  allow_failure: true

  script:
    # Install pyflakes - a lightweight Python linter
    - pip install pyflakes

    # Run pyflakes on our files.
    # It will print warnings like "imported but unused" or "undefined name".
    - python -m pyflakes app.py test_app.py

    - echo "Lint complete"


# ════════════════════════════════════════════════════════════
# STAGE 3: TEST
# Run our pytest tests and measure how much code they cover.
# This is the most important stage - if tests fail, we know our code is broken.
# ════════════════════════════════════════════════════════════
run-tests:
  stage: test
  image: python:3.11-alpine

  script:
    # Activate the venv that was saved as an artifact in Stage 1.
    # GitLab automatically downloads artifacts from previous stages.
    - source venv/bin/activate

    # Run pytest with these flags:
    # -v                          = verbose, show each test name + pass/fail
    # --cov=app                   = measure coverage of app.py
    # --cov-report=term-missing   = print which lines are NOT covered
    # --cov-report=xml:coverage.xml = save coverage as XML (GitLab reads this)
    # --junitxml=report.xml       = save test results as XML (GitLab reads this)
    - pytest test_app.py -v
        --cov=app
        --cov-report=term-missing
        --cov-report=xml:coverage.xml
        --junitxml=report.xml

  artifacts:
    # "when: always" = save artifacts even if the job fails.
    # Important! We want the test report even when tests fail,
    # so we can see WHICH tests failed in the GitLab UI.
    when: always
    reports:
      # Tell GitLab this is a JUnit test report.
      # GitLab will parse it and show a "Tests" tab on the pipeline page
      # with individual test names, pass/fail status and duration.
      junit: report.xml

      # Tell GitLab this is a coverage report.
      # GitLab will display the coverage % on the pipeline and MR pages.
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
    paths:
      - report.xml
      - coverage.xml
    expire_in: 1 week

  # This regex extracts the coverage % from the job log output.
  # pytest-cov prints a line like: "TOTAL   50   0   100%"
  # GitLab uses this regex to find that % and display it as a badge.
  coverage: '/TOTAL.*\s+(\d+%)$/'


# ════════════════════════════════════════════════════════════
# STAGE 4: BUILD
# Package the app and stamp it with build information.
# In real projects this is where you'd compile code or build a Docker image.
# ════════════════════════════════════════════════════════════
build-package:
  stage: build
  image: python:3.11-alpine

  script:
    - pip install build

    # Create a dist/ folder (short for "distributable")
    - mkdir -p dist

    # Copy our app into the dist folder
    - cp app.py dist/

    # Create a BUILD_INFO file stamped with pipeline metadata.
    # These are built-in GitLab CI variables - automatically available in every job:
    # $CI_PIPELINE_IID      = pipeline number (1, 2, 3...)
    # $CI_COMMIT_SHORT_SHA  = first 8 chars of the git commit hash
    # $CI_COMMIT_REF_NAME   = branch name (e.g. "main")
    - echo "Build number $CI_PIPELINE_IID"    >  dist/BUILD_INFO
    - echo "Commit $CI_COMMIT_SHORT_SHA"      >> dist/BUILD_INFO
    - echo "Branch $CI_COMMIT_REF_NAME"       >> dist/BUILD_INFO

    # Print the file so we can see it in the job log
    - cat dist/BUILD_INFO

  artifacts:
    paths:
      - dist/         # Save the dist/ folder for the deploy stage
    expire_in: 1 week


# ════════════════════════════════════════════════════════════
# STAGE 5: DEPLOY
# Ship the built package to production.
# In real projects this might: push to a server, update Kubernetes,
# release to PyPI, or trigger a cloud deployment.
# ════════════════════════════════════════════════════════════
deploy-production:
  stage: deploy
  image: alpine:latest

  # when: manual = this job has a ▶ PLAY BUTTON in the GitLab UI.
  # It will NOT run automatically - someone must click it.
  # This is a safety gate - you decide when to deploy, not the pipeline.
  when: manual

  # only: main = this job only EXISTS when running on the "main" branch.
  # Pushing to a feature branch will NOT show this job at all.
  # This prevents accidentally deploying unfinished feature branches.
  only:
    - main

  script:
    # $GITLAB_USER_LOGIN = built-in variable, the GitLab username who triggered this
    - echo "Deploying build $CI_PIPELINE_IID to production..."
    - echo "Commit $CI_COMMIT_SHORT_SHA by $GITLAB_USER_LOGIN"

    # Read the BUILD_INFO artifact saved by the build stage
    # GitLab automatically downloads artifacts from all previous stages
    - cat dist/BUILD_INFO

    - echo "Deploy successful!"
    
```
